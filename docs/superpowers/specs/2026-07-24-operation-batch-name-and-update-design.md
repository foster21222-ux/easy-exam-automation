# 运控批次名称与批次信息修改设计

日期：2026-07-24  
状态：已完成方案评审并经用户确认

## 1. 目标

在现有“项目管理 → 运控协同 → 建批次”流程中补充两项能力：

1. 在业务需求单中生成并允许人工编辑批次名称，创建批次页面继续只读使用该值。
2. 批次创建后，仅在受管字段发生实际变化时提示“可修改”，经配置台统一确认后，自动修改运控批次概况和考试日程，并回读校验。

本设计不改变项目名称，也不扩大到人员、结算、任务单或其它运控配置。

本设计取代 `2026-07-23-operation-personnel-task-send-design.md` 中“批次名称不修改”的限制，但只由独立的批次修改流程执行；人员任务发送流程仍不得自行修改批次基础信息。

## 2. 已确认的业务规则

### 2.1 批次名称

- 批次名称放在业务需求单中。
- 默认格式为 `客户简称考试类型简称_YYYY年M月`。
- 示例：`湖北邮政社招_2026年8月`。
- 客户简称和考试类型简称只能由确定性规则生成，不使用 LLM 猜测。
- 初始规则至少包含：
  - `中国邮政集团公司湖北省分公司` → `湖北邮政`
  - `社会招聘考试` → `社招`
- 未命中简称规则时保留对应原文，不编造简称。
- 年月取易考需求单 1 的正式考试开始时间。
- 日期无效或缺失时不生成不完整名称，提示用户补充或手工填写。

### 2.2 自动值与人工值

- 初次生成业务需求单时自动生成批次名称。
- 用户尚未手工修改时，批次名称随客户简称依据、考试类型简称依据或需求单 1 的正式考试月份重新计算。
- 用户手工编辑后，模式切换为 `manual`，后续来源变化不得覆盖人工值。
- 人工模式下来源变化只提示“批次名称可能需要调整”。
- 提供“恢复自动生成”操作；执行后重新按当前来源计算并切回 `auto`。

### 2.3 项目名称

- 业务需求单中的项目名称保持只读。
- 运控批次概况中的项目名称不在本功能修改范围内。
- 测试环境已有的项目名称和项目编码不一致放行规则保持不变。

### 2.4 考试日程

- 每份易考需求单对应一条运控考试日程。
- 易考需求单 1 对应日程 1，需求单 2 对应日程 2，以此类推。
- 日程受管字段只有：
  - 考试名称
  - 正式考试开始时间
  - 正式考试结束时间
- 科目信息变化不触发批次修改。
- 允许在末尾增加易考需求单，并在运控末尾新增对应日程。
- 批次创建后不允许删除已有易考需求单，也不允许自动删除运控日程。
- 若外部数据导致需求单数量减少，状态转为冲突并阻断自动修改，保留运控原日程等待人工处理。

### 2.5 批次概况考试日期

- 运控批次概况中的考试开始日期和考试结束日期属于受管字段，精确到日。
- 所有日程按实际时间排序：
  - 考试开始日期取最早一场的开始日期。
  - 考试结束日期取最晚一场的结束日期。
- 跨天日程使用实际结束日期，不按开始日期截断。

### 2.6 初次创建时的日程完整性

一条完整日程必须同时具有：

- 非空考试名称。
- 可解析的正式考试开始时间。
- 可解析的正式考试结束时间。
- 结束时间晚于开始时间。

多份易考需求单采用全有或全无规则：

- 全部需求单日程完整时，创建批次后统一创建全部考试日程。
- 任意一份需求单日程不完整时，初次创建一条考试日程也不创建。
- 批次本身仍允许创建，概况字段继续按现有建批次规则生成。
- 批次创建后显示“等待补全日程”并列出缺失项。
- 全部日程补齐后状态切换为“可修改”，通过批次修改流程一次性创建全部日程，并同步概况考试日期。

## 3. 方案选择

采用“受管快照对比 + 执行时运控回读”。

不采用仅凭变更历史判断，因为字段改回原值仍可能误报；不采用每次打开项目都读取运控，因为可见浏览器自动化较慢且会抢占窗口。

系统维护两个规范化快照：

- `desiredSnapshot`：由当前业务需求单和易考需求单计算的期望值。
- `appliedSnapshot`：最近一次已确认同步到运控并回读成功的值。

页面状态只比较这两个快照。真正执行修改前，再只读检查运控当前值是否仍与 `appliedSnapshot` 一致。

## 4. 数据模型

### 4.1 业务需求单批次名称

业务需求规范化模型新增：

- `batch_name`
- `batch_name_mode`：`auto` 或 `manual`
- `batch_name_auto_value`

泛微原始快照的可编辑字段中显示“批次名称”。项目名称控件显示为只读。

### 4.2 受管快照

批次配置新增版本化状态：

```json
{
  "operationBatch": {
    "managedSnapshot": {
      "batchName": "湖北邮政社招_2026年8月",
      "examStartDate": "2026-08-22",
      "examEndDate": "2026-08-23",
      "schedules": [
        {
          "requirementIndex": 0,
          "name": "湖北邮政社会招聘考试",
          "start": "2026-08-22T09:00:00",
          "end": "2026-08-22T11:00:00"
        }
      ]
    },
    "managedSnapshotVersion": 1,
    "lastManagedSyncAt": "ISO-8601",
    "managedEvents": []
  }
}
```

快照只包含本功能受管字段，不包含项目名称、科目、人员或其它运控配置。

### 4.3 日程身份

- `requirementIndex` 是第一版唯一映射依据。
- 已有日程按索引修改，不因名称或日期变化而更换身份。
- 新增需求单只能追加，新增日程从当前最大索引之后追加。
- 索引缺口、数量减少、运控日程数量多于已应用快照时均阻断，不猜测匹配。

## 5. 状态机

建批次步骤新增以下展示状态：

- `success` / “已创建”：运控已同步，当前受管字段无差异。
- `waiting_schedule` / “等待补全日程”：批次已创建，但初建时至少一份需求单日程不完整。
- `update_available` / “可修改”：期望快照与已应用快照存在受管字段差异，且输入完整、允许自动修改。
- `updating` / “修改中”：运控修改尝试正在执行。
- `update_conflict` / “修改冲突”：运控当前值、日程数量或身份与已应用快照不一致。
- `update_failed` / “修改失败”：自动化在确认修改前失败，或修改结果无法完整回读验证。

以下变化触发重新计算：

- 业务需求单批次名称变化。
- 易考需求单考试名称变化。
- 易考需求单正式考试开始或结束时间变化。
- 新增易考需求单。
- 日程从不完整变为全部完整。

以下变化不触发：

- 科目信息变化。
- 除批次名称外的非受管业务字段变化，包括只读项目名称。
- 内容任务、人员任务和实际执行数据变化。

只有规范化后的值发生实际变化才显示“可修改”；字段改回已应用值后自动恢复“已创建”。

## 6. 页面交互

### 6.1 业务需求单

- “批次名称”使用普通文本输入框。
- 自动模式显示“自动生成”来源标记。
- 人工修改并保存后显示“人工设置”来源标记。
- 人工模式显示“恢复自动生成”按钮。
- 项目名称显示但不可编辑。
- 保存继续生成平台内部修改、自动确认的版本和审计记录。

### 6.2 创建批次页面

- 页面布局和创建按钮保持不变。
- 批次名称只读展示业务需求单的当前值。
- 创建接口不得接受页面临时覆盖批次名称。
- 批次名称为空时阻断创建并引导用户返回业务需求单补充。

### 6.3 批次修改

状态为“可修改”时，建批次详情显示“修改批次信息”按钮。

点击后先执行只读预检，并在配置台统一展示：

- 批次名称：当前值 → 期望值。
- 概况考试开始日期：当前值 → 期望值。
- 概况考试结束日期：当前值 → 期望值。
- 每条已有日程的考试名称、开始时间和结束时间差异。
- 需要新增的日程序号及完整内容。

没有实际差异时不允许提交修改。

用户只需在配置台进行一次二次确认；运控页面不再要求用户确认。

## 7. 运控执行流程

### 7.1 初次创建

1. 使用业务需求单批次名称创建未发布批次。
2. 优先取得并保存批次代码，防止后续步骤失败时重复建批次。
3. 如果全部易考需求单日程完整：
   - 同步批次概况考试开始和结束日期。
   - 按需求单顺序创建全部考试日程。
   - 回读概况和日程，成功后保存 `managedSnapshot`。
4. 如果任意日程不完整：
   - 不进入考试日程创建。
   - 保存批次代码。
   - 状态设为 `waiting_schedule`。

创建批次成功但后续日程同步失败时，不得再次创建批次；状态进入 `update_failed`，只能继续批次修改或人工恢复。

### 7.2 修改预检

1. 通过批次代码精确进入目标批次。
2. 读取批次名称、概况考试日期和考试日程。
3. 校验运控当前受管值与 `appliedSnapshot` 一致。
4. 若运控被人工修改或日程数量异常，返回 `update_conflict`。
5. 一致时生成差异预览和一次性预览令牌。

### 7.3 修改执行

1. 校验预览令牌、项目版本和期望快照未变化。
2. 修改批次概况中的批次名称、考试开始日期和考试结束日期。
3. 按索引修改已有日程的考试名称、开始时间和结束时间。
4. 按索引顺序追加新日程。
5. 保存后关闭编辑状态并重新进入详情页。
6. 回读全部受管字段。
7. 全部一致才保存新 `managedSnapshot` 和成功事件。

运控发布状态不影响本流程，不增加取消发布、重新发布或回退状态操作。

## 8. 接口与协调

新增项目级接口：

- `GET /api/tasks/:taskId/operation-batch/update-state`
  - 返回期望快照、已应用快照、缺失日程和页面状态。
- `POST /api/tasks/:taskId/operation-batch/update-preview`
  - 只读检查运控并返回差异与预览令牌。
- `POST /api/tasks/:taskId/operation-batch/update`
  - 接受已确认预览令牌，启动异步修改。
- `GET /api/tasks/:taskId/operation-batch/update-attempts/:attemptId`
  - 返回 checkpoint、倒计时、错误和最终回读结果。

建批次创建、批次修改和人员任务共用现有运控专用浏览器锁，避免同时抢占同一个浏览器资料目录。

## 9. 幂等、冲突与恢复

- 同一项目同时只允许一个批次创建或修改尝试。
- 预览令牌绑定任务 ID、当前需求版本和期望快照指纹。
- 期望值在用户确认后变化时拒绝使用旧令牌。
- 当前期望快照与已应用快照一致时拒绝重复修改。
- 不自动覆盖未记录的运控人工修改。
- 自动化结果不确定时不盲目重试写操作；先重新进入详情页只读对账。
- 回读已经等于期望快照时，将尝试对账为成功。
- 回读仍等于原已应用快照时，允许安全重试。
- 回读处于两者之间时阻断人工处理。

审计至少记录：

- 修改前受管快照。
- 期望快照。
- 用户确认人和确认时间。
- 实际回读快照。
- 新增和修改的日程索引。
- 成功、冲突或失败原因。

## 10. 错误提示

- 批次名称缺失：提示返回业务需求单补充。
- 日期缺失或无效：列出具体需求单和字段。
- 日程未全部完整：显示“等待补全日程”，不创建任何日程。
- 删除需求单或日程数量减少：提示“不允许删除已同步日程，需要人工处理”。
- 运控当前值与已应用快照不一致：显示具体不一致字段并阻断。
- 回读不一致：显示期望值和实际值，不标记修改成功。

## 11. 测试

### 11.1 纯业务测试

- 精确简称映射和未知名称回退原文。
- 名称格式无首个下划线：`湖北邮政社招_2026年8月`。
- 自动模式随来源变化，人工模式不被覆盖，恢复自动后重新计算。
- 无有效日期时不生成不完整名称。
- 多日程概况日期取最早开始日和最晚结束日。
- 任意一份日程不完整时初建日程集合为空。
- 全部补齐后生成按需求单顺序排列的完整日程。
- 科目变化不改变受管快照指纹。
- 新增需求单产生追加日程；数量减少产生冲突。

### 11.2 服务端与状态测试

- 批次代码先于日程同步结果持久化。
- `waiting_schedule`、`update_available`、`update_conflict` 和 `update_failed` 状态转换。
- 无差异、旧预览令牌、并发尝试和项目版本变化均被拒绝。
- 修改成功后原子保存回读快照和审计事件。
- 失败或不确定结果不伪造成功。

### 11.3 Runner 测试

- 精确读取批次概况和考试日程。
- 只修改批次名称、概况日期和日程名称/时间。
- 按索引更新已有日程并在末尾新增。
- 不点击删除日程、取消发布或其它非目标控件。
- 保存后重新进入页面并回读完整快照。
- 部分写入、页面关闭和结果不确定时进入对账分支。

### 11.4 UI 测试

- 业务需求单显示批次名称、模式和恢复自动按钮。
- 项目名称只读。
- 创建批次页没有新增批次名称编辑框。
- 正确显示“等待补全日程”“可修改”和冲突状态。
- 修改预览完整展示概况与逐日程差异。
- 没有差异时确认按钮不可用。

## 12. 验收标准

1. 示例项目默认生成 `湖北邮政社招_2026年8月`。
2. 人工修改批次名称后刷新页面仍保留，且后续自动计算不覆盖。
3. 创建批次始终使用业务需求单中的批次名称。
4. 多份需求单中任意日程不完整时，批次可以创建，但运控不创建任何考试日程。
5. 全部日程完整后状态显示“可修改”，确认后一次性创建全部日程。
6. 考试名称或时间变化后只修改对应日程；科目变化不提示批次修改。
7. 多天日程使概况日期准确更新为最早开始日和最晚结束日。
8. 新增需求单只追加日程；删除或数量减少被阻断。
9. 修改完成必须以运控回读一致为成功依据。
10. 全量 Node 测试通过，并在 8765 测试环境验证业务需求编辑、状态提示、修改预览和失败恢复。

## 13. 非目标

- 修改运控项目名称或项目编码。
- 根据科目信息修改考试日程。
- 删除运控考试日程。
- 修改人员、结算、考站、内容任务或任务单配置。
- 自动取消发布或重新发布批次。
- 直接调用或逆向运控未公开接口。
- 使用 LLM 生成客户或考试类型简称。

## 14. 历史项目轻量兼容

历史项目可能在“批次名称”字段上线前已经保存，因此
`fanweiSource.raw.fields` 中没有“批次名称”，页面也就没有可编辑输入框。

兼容规则：

- 读取项目详情时，仅在返回给页面的任务副本中补充批次名称编辑状态；
  不扫描、不批量更新历史数据库。
- 默认值继续调用服务端既有 `defaultOperationBatchName`，不在前端复制简称规则。
- 优先保留历史记录中已有的人工批次名称；缺失时使用当前客户名称、项目名称和
  第一份易考需求单考试日期生成自动名称。
- 即使日期不完整、无法生成默认名称，也返回空的“批次名称”字段，让用户能够
  手工填写。
- 用户未点击“保存修改”时，不产生版本、审计或数据库写入；保存后继续走现有
  泛微业务需求修改接口。
- 新项目和已经包含批次名称的项目行为保持不变。
