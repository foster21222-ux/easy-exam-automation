# 运控批次创建结果对账设计

## 背景与证据

项目 `ff4a7062-2c29-4e31-97e8-de39b0bb79f2` 已在运控创建批次，但本地 `operationBatchCode` 为空，保存状态为 `failed`，错误为“创建完成，但未能从详情页读取批次代码”。现有创建流程在跳转到批次详情页后立即扫描整页文本，只接受三位大写字母加六位数字的代码；详情页暂未渲染代码或页面结构变化时，外部创建已经完成，本地却被当成普通可重试失败。项目工作流又只按本地批次代码判断完成状态，因此页面继续显示“可执行”，再次提交会撞上运控已有批次。

## 目标

1. 创建提交后优先等待详情页出现批次代码，读取失败时按批次名称回查批次列表。
2. 外部可能已经创建但仍无法取得代码时，保存为“待同步”，不得再次执行创建。
3. 提供只读查询运控列表并回填本地代码的对账动作，用于恢复当前项目和同类历史记录。
4. 对账成功后复用现有结果写入逻辑，回填批次代码、详情地址、状态和事件，工作流随即显示已完成。
5. 自动测试不得连接运控或创建真实批次。

## 方案比较

### 方案 A：仅依赖人工补录

改动最少，但把可自动恢复的问题长期留给人工，重复创建风险仍然存在，不采用。

### 方案 B：详情等待、列表回查和显式待同步状态（采用）

保留现有可见浏览器自动化，在创建边界增加条件等待与列表对账；无法确认结果时阻止再次创建，并提供独立的只读对账入口。改动集中在批次 runner、服务端状态写入和项目工作流展示，能直接恢复当前数据。

### 方案 C：直接调用运控内部接口

理论上更稳定，但当前没有经过验证、受支持的运控 API 契约，也会引入认证和版本耦合。本次不扩大边界。

## 设计

### Runner

- 将批次列表查询抽成可单测的结果解析和查找函数。
- 创建提交后等待详情页出现符合格式的批次代码；若未出现，不立即报普通失败，而是查询批次列表。
- 列表查询必须同时匹配目标批次名称，再从该匹配结果中提取代码，避免误取页面上其他批次。
- 新增只执行列表查询的 `runOperationBatchReconciliation`，它复用同一浏览器配置和登录状态，但不会点击“创建批次”。
- 详情和列表都无法确认结果时抛出带稳定错误码的待同步错误，服务端不依赖中文错误文案判断状态。

### 服务端状态

- 新增 `reconciliation_required` 状态，保存错误码、错误信息、草稿和更新时间。
- 创建接口遇到该状态时拒绝再次创建，返回明确提示，防止重复批次。
- 新增项目级对账接口。它只读取运控列表；找到结果后调用现有 `applyOperationBatchResult` 原子回填，找不到时保留待同步状态。
- 普通表单校验、登录失败或创建前失败仍保存为 `failed`，允许修正后重试。

### 页面和工作流

- 没有代码且状态为 `reconciliation_required` 时，建批次步骤显示“待同步”，不显示“可执行”。
- 创建按钮禁用，显示独立的“查询并同步已有批次”动作。
- 对账成功后刷新项目和工作流，现有批次代码即成为完成状态的唯一依据。
- 现有“手动补录批次代码”保留为最终人工兜底。

## 错误处理与安全边界

- 对账查询只使用当前项目草稿中的批次名称，不创建、编辑或发布任何运控数据。
- 查询得到零条或无法唯一确认时，不猜测批次代码，不改变为成功。
- 仅在得到合法代码后写入本地完成状态。
- 当前项目恢复时先执行只读对账；只有成功读取到运控代码才回填运行时数据库。

## 测试与验收

1. 单元测试先证明：详情页没有代码时，现有实现不会返回列表回查结果。
2. 测试创建结果解析：详情代码可读取、详情缺失后列表命中、列表未命中进入待同步。
3. 测试状态机：待同步状态阻止再次创建；对账成功复用现有结果回填；对账失败不伪造代码。
4. UI 测试：待同步显示正确标签，创建按钮不再可用，对账按钮可用。
5. 运行相关 Node 测试和全量 Node 测试；如项目有独立 Python 测试，再运行全量 Python 测试。
6. 同步到 8765 后，对当前项目仅执行对账接口，核对本地批次代码和“已完成”状态，不发起真实创建。

## 非目标

- 不替换现有 Playwright 可见浏览器方案。
- 不接入未经验证的运控内部 API。
- 不修改批次业务字段、发布状态或运控侧已有数据。
- 不自动清除“有变更请确认”；该提示属于来源变更审核，与批次代码同步独立。
