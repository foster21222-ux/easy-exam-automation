# 运控人员任务单配置与发送设计

日期：2026-07-23  
状态：已完成方案评审并经用户确认

## 1. 目标

在项目管理主流程的“运控协同 → 人员任务”中，实现标准“ATA 监考－分散在线监考”人员任务单的完整配置与发送：

1. 从当前项目、配置需求、运控批次和实际考生数据生成版本化人员任务草稿。
2. 读取运控当前状态，识别需要补齐或修改的考试日程、人员配置、考务需求和落实日期。
3. 在一个二次确认窗口中统一展示运控修改、任务单内容、收件人与抄送人。
4. 用户确认后，首次发送时按需发布批次，完成运控配置并使用运控内置“发送任务单”机制发送。
5. 以运控右上角发送记录作为唯一成功依据。
6. 需求发生变化时，精确修改对应运控配置，填写变化摘要并允许重发。
7. 通过 checkpoint、状态回读和发送记录对账，避免重复发送及不确定结果下的自动重试。

## 3. 范围

### 3.1 第一版支持

- 标准“ATA 监考－分散在线监考”任务单。
- 首次发送和基于已确认需求变更的重发。
- 一个运控批次对应一张人员任务单。
- 多个正式考试场次和科目按日程逐行配置。
- 试考仅在配置需求明确要求安排监考时纳入。
- 运控批次按需自动发布。
- 测试环境和正式环境的固定收件规则。
- 配置差异预览、统一二次确认、异步执行、倒计时、checkpoint 和结果对账。

### 3.2 第一版不支持

- 高端项目补充需求任务单。
- 集中在线监考。
- 考站及督考。
- 人员－支持。
- 客服呼入、客服呼出、考试培训或其它任务单。
- 通过 Outlook SMTP 代发人员任务单。
- 修改项目编码、项目名称、批次名称、项目部归属等批次基础信息。
- 运控外部修改的三方合并或自动覆盖。
- 手工标记发送成功。
- 直接调用或逆向运控未公开网络接口。

检测到不支持范围时，系统必须阻断并说明人工处理入口，不得降级为其它任务类型。

## 4. 方案选择

采用“版本化业务模型 + Playwright 可见客户端自动化”：

- 业务模型负责草稿、来源、版本、差异、默认值、指纹、状态和审计。
- Playwright 使用现有运控专用浏览器资料目录，操作录制验证过的页面和控件。
- 服务端协调器负责专用浏览器锁、项目锁、checkpoint、异步尝试和持久化。
- 项目详情 UI 负责统一确认、执行进度、倒计时、成功记录和恢复操作。

不采用运控内部接口直连，因为接口未公开且未验证稳定性；不采用半自动方案，因为无法满足完整配置、发送、重发和对账目标。

## 5. 系统架构

### 5.1 人员任务业务模型

新增独立的纯业务模块，职责包括：

- 生成人员任务草稿。
- 计算考试日程与稳定日程代码。
- 计算监考人数和来源说明。
- 应用环境收件规则。
- 生成影响任务单内容的需求指纹。
- 比较上次成功版本和当前版本。
- 生成重发变化摘要。
- 校验首次发送、重发、阻断和不支持条件。
- 生成可持久化的状态补丁和审计事件。

该模块不得访问浏览器、数据库或网络。

### 5.2 运控人员任务执行器

新增 Playwright 执行器，职责包括：

- 精确定位批次代码和批次详情。
- 读取批次发布状态。
- 读取考试日程、人员配置、考务需求和落实日期。
- 读取分散在线监考任务单和实时人员目录。
- 生成可比较的运控快照。
- 按确认差异执行批次发布和配置修改。
- 使用运控内置发送机制选择固定收件人与抄送人。
- 读取右上角发送记录。

执行器只接受已经校验的领域指令，不自行推断业务默认值。

### 5.3 服务端协调器

建批次和人员任务必须共用同一个运控专用浏览器锁，避免同时打开相同持久化资料目录。服务端还需提供：

- 单项目人员任务锁。
- 异步发送尝试。
- checkpoint 持久化。
- 新鲜项目状态重读。
- 预览令牌和需求版本校验。
- 发送结果对账。
- 权限与项目归属校验。

### 5.4 项目详情 UI

现有禁用的“人员任务接口待接入”替换为真实人员任务操作。UI 不复制一套独立工作流，而是继续使用现有“运控协同”人员步骤卡及详情面板。

## 6. 数据来源与映射

### 6.1 批次基础信息

来源：现有建批次结果和运控回读。

人员模块只校验以下字段，不修改：

- 批次代码。
- 项目编码。
- 项目名称。
- 批次名称。
- 项目部归属。
- 项目经理。
- 系统类型。

任一字段不一致时阻断，要求人工在配置平台和运控中调整一致。

### 6.2 考试日程

来源：当前已确认配置需求中的正式考试场次、科目、开始时间、结束时间、时长和提前登录分钟数。

规则：

- 同一批次生成一张任务单。
- 全部正式场次按时间升序排列。
- 每个场次保留自身提前登录分钟数。
- 试考只有在配置需求明确要求试考监考时加入。
- 日程时长由开始和结束时间计算，并与配置需求中的时长交叉校验。
- 缺少日期、时间、科目或有效时长时阻断。

### 6.3 稳定日程代码

- 首次发送时按场次时间顺序生成 `1、2、3…`。
- 每个日程条目在首次预览时生成并持久化 `scheduleEntryId`；该标识绑定需求单稳定 ID、正式/试考类型和科目稳定键，不包含可修改的日期、时间或名称。
- 科目已有课程代码时使用课程代码作为稳定键；尚无课程代码时生成并持久化人员任务专用科目键。
- 已发送后保留已存在场次的日程代码。
- 新增场次使用当前最大代码之后的新代码。
- 修改日期、时间或科目名称时沿用原 `scheduleEntryId` 和日程代码。
- 删除场次必须通过 `scheduleEntryId` 和日程代码唯一匹配。
- 删除项在统一确认窗口中明确列出。
- 无法唯一匹配时阻断，不猜测删除。

### 6.4 人员配置

- 人员服务类型：`ATA 监考－分散在线监考`。
- 人员落实平台：固定 `悦站`。
- 监考登录监控：固定 `是`。
- 监考比例：默认 `1:50`。
- 最早登录系统时间：取所有正式场次提前登录分钟数的最大值。

监考人数计算：

1. 优先使用已导入考生的实际同时开考峰值。
2. 无实际考生数据时，使用运控批次“预估单场最大科次数”。
3. 两者都缺失时不自动计算，要求用户手工填写。
4. 自动计算为基数除以 50 后向上取整，最少 1 人。

监考人数和比例允许在统一确认窗口中修改；保存后形成平台内部修改、自动确认的版本审计。

### 6.5 人员日期

三个日期都允许用户修改：

- 人员落实开始日期：默认首次发送当天。
- 人员落实结束日期：默认最早正式考试日期前 3 天。
- 人员名单提交日期：默认最早正式考试日期前 3 天。

若默认值已过期、开始晚于结束、或区间无效，则对应字段不预设并要求用户选择。重发时带出运控当前值；用户修改后，必须先同步运控对应设置并回读成功，才能发送。

### 6.6 收件人与抄送人

正式环境：

- 收件人：`拓展二部` 中精确匹配 `唐润梅`。
- 抄送人：`结算组` 中全部人员，必须精确为 4 人。

测试环境：

- 收件人：`演练组` 中精确匹配 `张乐翔`。
- 抄送人：空。

规则：

- 通过明确配置的环境标识选择规则，不根据页面猜测环境。
- 未知环境阻断。
- 组名、人员名、重名或人数不匹配时阻断并显示实际匹配结果。
- 测试环境不得回退使用正式收件人。
- 固定收件信息在统一确认窗口中只读展示，不允许临时改人。

## 7. 版本、指纹与重发

人员任务需求指纹只包含会影响任务单或运控人员配置的规范化字段：

- 批次身份。
- 日程及稳定代码。
- 科目和时间。
- 提前登录分钟数。
- 人员日期。
- 人员平台和监考类型。
- 监考人数、比例和登录监控。
- 是否包含试考监考。
- 环境收件规则版本。

首次成功发送后保存成功指纹和运控配置快照。

规则：

- 当前指纹与上次成功指纹完全一致时，前端禁用重发，服务端也返回冲突错误。
- 已确认需求变化导致指纹变化时，状态为 `changes_pending`。
- 重发前先比较并修改对应运控配置。
- 系统根据两个指纹对应的版本差异自动生成变化摘要。
- 项目负责人可补充或修改变化摘要。
- 重发时变化摘要必填，并纳入统一二次确认和审计。
- 存在客户或微信群待审核变更时，首次发送和重发都阻断。

## 8. 运控外部修改冲突

系统不做三方合并。

首次发送：

- 运控目标字段为空时，可以作为待补齐项。
- 运控已有非空值且与平台期望值不一致时阻断。

重发：

- 运控当前配置必须与上次成功发送时保存的运控快照一致。
- 不一致说明运控网站被人工修改，直接进入 `operation_conflict`。
- 用户必须人工把配置平台和运控调整一致后重新检查。

系统不得静默覆盖、不得自动把运控值同步回平台、不得让用户在冲突窗口选择一边覆盖另一边。

## 9. 首次发送流程

1. 校验登录用户权限和项目归属。
2. 读取最新项目、批次、需求版本和待审核变更。
3. 生成本地人员任务草稿。
4. 取得运控浏览器锁和项目锁。
5. 只读打开批次详情并读取运控快照。
6. 读取分散在线监考任务单状态和实时人员目录。
7. 返回带有效期的统一确认预览。
8. 用户修改允许编辑的字段；服务端保存草稿和自动确认审计。
9. 用户点击唯一最终按钮“确认配置并发送任务单”。
10. 服务端重新读取项目版本和运控状态，验证预览未过期。
11. 批次未发布时执行发布；已发布时幂等跳过。
12. 回读确认批次状态为“已发布”。
13. 按 checkpoint 修改考试日程、人员配置、考务需求和落实日期。
14. 回读并验证每项配置。
15. 打开分散在线监考任务单。
16. 校验运控页面列出的发送条件全部满足。
17. 校验任务单内容与已确认草稿一致。
18. 精确选择环境对应的收件人和抄送人。
19. 点击运控内置发送并最终确认。
20. 等待并对账右上角新发送记录。
21. 保存成功指纹、运控快照、发送记录和审计事件。

批次发布作为首次人员任务流程的独立 checkpoint，统一确认窗口必须显示“本次将发布运控批次”。重发不重复发布。

预览令牌有效期固定为 10 分钟；项目需求版本、人员草稿版本、运控快照或收件目录匹配结果任一变化时立即失效，用户必须重新生成预览。

## 10. 重发流程

1. 当前需求指纹必须不同于上次成功指纹。
2. 校验不存在待审核外部变更。
3. 回读运控当前配置，必须与上次成功快照一致。
4. 生成运控修改清单和变化摘要。
5. 用户在统一确认窗口检查并补充变化摘要。
6. 按 checkpoint 修改新增、变更或删除的对应运控配置。
7. 回读确认配置与新草稿一致。
8. 打开任务单并校验内容。
9. 按当前环境规则重新匹配固定收件人和抄送人。
10. 使用运控内置机制发送。
11. 只有出现发送时间晚于本次尝试开始时间的新记录，才判定重发成功。
12. 保存新的成功指纹、运控快照、变化摘要和发送记录。

## 11. 状态机

主路径：

`waiting_batch → needs_review → ready → applying_config → sending → verifying → sent`

分支状态：

- `unsupported`：任务类型或高端补充需求不支持。
- `blocked_pending_change`：存在未审核外部需求变更。
- `operation_conflict`：平台和运控状态冲突。
- `changes_pending`：已发送后出现影响任务单的已确认变化。
- `failed_resumable`：配置步骤失败且可从 checkpoint 继续。
- `result_unknown`：两轮发送记录核对仍无结果。

`result_unknown` 不允许人工标记成功，只允许重新核对运控发送记录。

## 12. Checkpoint 与恢复

固定 checkpoint 顺序：

1. `inspect_batch`
2. `publish_batch`
3. `sync_exam_schedules`
4. `sync_personnel_config`
5. `sync_personnel_dates`
6. `sync_exam_service_requirements`
7. `verify_task_sheet`
8. `select_recipients`
9. `submit_send`
10. `verify_send_record`

每个 checkpoint 保存：

- 状态。
- 开始和完成时间。
- 输入版本和摘要。
- 运控回读摘要。
- 错误码和用户可读错误。

已成功写入运控的配置不自动回滚。继续执行前重新读取运控；状态与 checkpoint 不一致时进入冲突阻断。

## 13. 发送记录对账

点击最终确认后：

1. 第一阶段等待最多 30 秒。
2. UI 显示“正在等待运控发送记录”和逐秒倒计时。
3. 出现符合本次尝试的发送记录即成功。
4. 超时后关闭任务单弹窗。
5. 重新进入对应批次的分散在线监考发送页面。
6. 第二阶段再等待最多 30 秒并显示倒计时。
7. 仍无记录则进入 `result_unknown`。

首次发送需要出现首次发送记录。重发必须出现发送时间晚于本次尝试开始时间的新记录；历史旧记录不能证明本次发送成功。

点击运控最终确认后，自动化不得再次点击发送。`result_unknown` 只能进行只读重新核对。

## 14. 持久化模型

项目配置新增 `operationPersonnelTask`，至少包含：

- `schemaVersion`
- `environment`
- `status`
- `draft`
- `draftVersion`
- `sourceFingerprint`
- `lastSuccessfulFingerprint`
- `scheduleCodeMap`
- `lastOperationSnapshot`
- `checkpoints`
- `activeAttempt`
- `sendHistory`
- `changeSummary`
- `events`

发送历史记录至少包含：

- `attemptId`
- 首次发送或重发类型
- 操作者
- 环境
- 需求版本
- 草稿版本
- 指纹
- 收件人和抄送人
- 运控发送记录类型和时间
- 运控快照摘要
- 变化摘要
- 创建和完成时间

不保存运控登录凭据或完整人员目录。

## 15. API

保持最小接口面：

### `GET /api/tasks/:taskId/operation-personnel-task`

返回当前人员任务状态、草稿、历史、可用动作和阻断原因。

### `POST /api/tasks/:taskId/operation-personnel-task/preview`

只读检查最新项目和运控状态，返回统一确认预览及有有效期的预览令牌。

### `POST /api/tasks/:taskId/operation-personnel-task/send`

提交预览令牌、草稿版本和变化摘要。重新验证后启动异步尝试，返回 `202` 和 `attemptId`。

### `GET /api/tasks/:taskId/operation-personnel-task/attempts/:attemptId`

返回当前 checkpoint、倒计时阶段、剩余秒数、完成状态和错误。

### `POST /api/tasks/:taskId/operation-personnel-task/recheck`

仅在 `result_unknown` 状态下读取运控发送记录，不修改配置、不点击发送。

## 16. UI

人员步骤卡显示：

- 状态标签。
- 当前任务单版本。
- 上次成功发送时间。
- 是否存在需求变化。
- 阻断原因或当前执行步骤。

主操作文案：

- `检查并发送人员任务单`
- `检查变更并重新发送`
- `继续未完成流程`
- `重新核对发送记录`
- `内容未变化，不允许重复发送`

统一确认窗口包含：

1. 环境、项目、批次和需求版本。
2. 阻断项与发送条件。
3. 是否将发布批次。
4. 运控配置修改前后差异。
5. 完整考试日程。
6. 人员配置、日期、人数、比例和计算依据。
7. 固定收件人和抄送人的实际匹配结果。
8. 重发变化摘要。
9. 唯一最终确认按钮。

确认后窗口切换为步骤进度视图，不再弹出独立收件确认窗口。

## 17. 权限与审计

- 项目负责人只能操作自己负责的项目。
- 管理员可以操作所有项目。
- 两种角色都必须完成统一二次确认。
- 人工编辑允许字段时，按平台内部修改、自动确认规则保存版本审计。
- 每次预览、确认、配置、发送、对账、失败、恢复和冲突都记录事件。
- 固定收件规则只读，项目负责人和管理员都不能在发送窗口临时改人。

## 18. 测试

### 18.1 业务模型

覆盖：

- 多场次和多科目。
- 试考纳入与排除。
- 稳定日程代码的新增、修改和删除。
- 日期默认值及无效日期。
- 监考人数来源优先级和计算。
- 环境收件规则。
- 指纹不变禁止重发。
- 需求变化和变化摘要。
- 不支持类型及待审核变更阻断。

### 18.2 Playwright 执行器

使用模拟页面和响应覆盖：

- 批次精确匹配。
- 未发布批次发布和已发布幂等跳过。
- 日程和人员配置的精确读取与修改。
- 非空冲突阻断。
- 收件组、人员和结算组人数精确匹配。
- 最终发送只点击一次。
- 两段 30 秒倒计时。
- 首次发送和重发的新记录识别。
- 页面超时、弹窗关闭和重新进入。
- `result_unknown` 只读核对。

### 18.3 服务端

覆盖：

- 项目归属和管理员权限。
- 运控浏览器锁和项目锁。
- 新鲜任务重读。
- 过期预览令牌。
- 同内容重复发送。
- 异步尝试和 checkpoint。
- 服务重启后的失败可恢复状态。
- 审计及敏感数据边界。

### 18.4 UI

覆盖：

- 统一确认窗口的完整内容。
- 固定收件规则只读。
- 首次发送、重发、失败继续和重新核对动作。
- 当前项目切换时的异步响应隔离。
- 可见倒计时。
- 内容未变化时按钮和服务端双重阻断。

### 18.5 测试运控验收

只使用测试环境：

- 收件人固定为“演练组 / 张乐翔”。
- 无抄送。
- 完成一次首次发送。
- 验证右上角首次发送记录。
- 验证内容未变化时无法重发。
- 创建一条已确认、影响任务单的需求变化。
- 自动修改对应运控配置并填写变化摘要。
- 完成一次重发。
- 验证出现晚于重发尝试的新发送记录。

正式环境不在自动测试中发送。

## 19. 完成标准

只有同时满足以下条件，功能才可标记完成：

1. 业务、执行器、服务端和 UI 自动化测试全部通过。
2. 现有建批次、内容邮件、需求审核和其它工作流回归测试通过。
3. 测试运控首次发送和重发实测通过。
4. 同内容重复发送被前端和服务端阻断。
5. 发送结果不确定时未发生自动重复点击。
6. 测试收件规则和正式收件规则相互隔离。
7. 本地 8765 运行时原子同步后健康，运行时配置、SQLite、依赖和浏览器资料保持不变。
8. 设计、实现、测试证据和未解决事项均有明确记录。
