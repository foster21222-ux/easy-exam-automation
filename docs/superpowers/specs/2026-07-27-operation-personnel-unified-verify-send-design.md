# 人员任务统一校验并发送设计

日期：2026-07-27
状态：已完成方案确认，待实施

## 1. 目标

人员任务确认页允许用户集中调整人员日期和监考参数。编辑过程不得反复打开运控浏览器；用户确认后，系统统一重新读取运控状态，校验通过便立即使用运控内置机制发送，校验失败则阻断且不产生发送动作。

确认页中的考试日程必须展示运控真实“日程代码”，不得使用需求单序号、数组索引或系统自行生成的人员任务日程编号冒充。

## 2. 已确认业务规则

1. 人员任务发送前必须已有完整且与易考需求一致的运控考试日程。
2. 日程缺失、日程代码缺失或重复、批次待调整、日程冲突时，流程必须在发送确认前阻断。
3. 人员任务流程只读取并核验日程，不创建、修改或删除运控日程。
4. 确认页五个可编辑字段为：
   - 人员落实开始日期；
   - 人员落实结束日期；
   - 人员名单提交日期；
   - 监考人数；
   - 监考比例。
5. 编辑上述字段时只更新配置台内存中的待发送值，不请求后端预览接口，也不打开运控浏览器。
6. 最终按钮统一承担“确认、校验、发送”职责。校验通过后直接发送，不增加第三次确认。
7. 测试环境收件人为演练组张乐翔，抄送为空；生产环境沿用已确认的固定收件规则。

## 3. 用户流程

### 3.1 打开确认页

用户点击“检查并发送人员任务单”后，系统执行一次只读预览：

1. 检查批次调整状态和受管日程门槛；
2. 精确定位运控批次；
3. 读取人员任务单、运控日程代码、当前人员参数、固定收件人和发送记录；
4. 校验日程代码唯一且日程内容与易考需求一致；
5. 生成配置台确认页。

任一前置条件不满足时，不打开可发送确认页，直接显示明确的阻断原因。

### 3.2 集中编辑

确认页展示：

- 运控环境、项目、批次和需求版本；
- 运控修改前后；
- 五个可编辑字段；
- 只读考试日程表；
- 固定收件人和固定抄送人；
- 重发时的变化摘要。

只读考试日程表列为：

| 日程代码 | 考试名称 | 开始时间 | 结束时间 |
| --- | --- | --- | --- |
| 运控实际代码 | 运控读取值 | 运控读取值 | 运控读取值 |

用户修改五个字段时，页面只更新本地待发送数据并标记“内容已修改，发送时将统一重新校验”，不关闭确认页、不刷新预览、不打开浏览器。

### 3.3 统一校验并发送

最终按钮文案为“确认以上内容并校验发送”。

点击后，前端一次性提交：

- 当前预览令牌；
- 五个最终编辑值；
- 重发变化摘要。

服务端在既有任务锁和运控浏览器锁内：

1. 重新读取最新项目和需求；
2. 检查需求版本、批次调整状态和受管日程指纹；
3. 精确匹配批次代码和批次名称；
4. 重新读取运控日程代码、日程内容、人员参数、收件人和发送条件；
5. 将五个最终编辑值生成本次发送目标；
6. 对比确认时数据与最新运控数据；
7. 校验通过后执行必要的人员参数修改；
8. 在最终点击发送前再次读取日程和收件人；
9. 仍然一致时，立即使用运控内置机制发送。

校验与发送属于同一次受锁执行，不在两者之间返回前端等待再次确认。

## 4. 日程代码来源

日程代码只接受运控任务单日程表中“日程代码”列的可见值。

系统必须验证：

- 每条日程代码非空；
- 日程代码在当前任务单内唯一；
- 按考试名称、开始时间和结束时间，运控日程与受管日程一一对应；
- 页面展示使用对应运控日程代码。

需求单序号、`requirementIndex`、数组位置和历史 `scheduleCodeMap` 均不得作为确认页日程代码的替代来源。

## 5. 阻断与提示

统一校验失败时：

- 不进入不可逆发送检查点；
- 不点击运控发送按钮；
- 不产生发送成功记录；
- 保留用户当前编辑值；
- 恢复最终按钮，使用户修正后可以重试；
- 显示可操作的中文提示。

主要提示包括：

- “批次信息尚未完成同步，请先在建批次环节完成批次信息修改”；
- “运控日程代码缺失或重复，无法确认唯一考试日程”；
- “运控日程与当前易考需求不一致，请先修改批次信息”；
- “人员任务单收件人与固定规则不一致，请人工检查”；
- “运控任务单发送条件未全部满足，请检查运控配置”。

若最终发送按钮已经点击但结果无法确认，继续沿用现有“发送结果未知，只能重新核对发送记录”恢复机制。

## 6. 数据与接口调整

### 6.1 预览结果

预览结果增加只读展示用的运控日程代码映射。该映射来自本次运控读取结果，不写回易考需求单，也不进入批次日程管理数据。

### 6.2 发送请求

发送请求在现有预览绑定之外增加五个最终编辑值。服务端负责重新验证、规范化并生成最终目标，不信任前端提交的只读日程、批次身份或收件人。

### 6.3 预览令牌

预览令牌继续绑定：

- 需求版本；
- 批次身份；
- 受管日程指纹；
- 运控快照；
- 固定收件人；
- 环境和任务版本。

最终编辑值在发送请求进入任务锁后应用；任何源数据漂移仍然阻断发送。

## 7. 安全边界

- 不读取或修改运控数据库。
- 不绕过运控内置发送机制。
- 人员任务流程不写考试日程。
- 测试环境和生产环境收件规则保持隔离。
- 日程代码只用于展示、精确核验和审计，不作为易考需求单的业务字段。
- 校验失败必须发生在不可逆发送检查点之前。

## 8. 验收标准

1. 连续修改五个字段不会产生任何预览 API 请求或浏览器操作。
2. 点击最终按钮只启动一次统一运控执行。
3. 校验通过后无需第三次确认，直接完成运控内置发送。
4. 校验失败时发送按钮未被点击，页面保留编辑值并显示明确原因。
5. 确认页显示真实运控日程代码，不出现 `0`、需求单序号或数组索引替代值。
6. 日程代码缺失、重复或不能一一匹配时阻断。
7. 需求日程在编辑期间发生变化时阻断，必须先完成批次调整。
8. 最终点击发送前日程或收件人发生变化时阻断并标记为可恢复失败。
9. 人员任务所有执行路径均不调用日程新增、修改或删除方法。
10. 首次发送、需求变更后的再次发送和发送记录核对流程保持可用。
11. 浅色和深色主题下，日程代码、编辑状态和阻断提示均清晰可读。

## 9. 测试范围

- 前端事件测试：字段编辑只更新本地状态，不调用预览接口。
- 前端请求测试：最终按钮一次性提交预览令牌、五个编辑值和变化摘要。
- 领域测试：五个字段规范化、日程代码映射和缺失/重复阻断。
- 服务测试：发送时重新应用编辑值并重新检查需求、批次与日程。
- 执行器测试：按运控日程代码一一匹配，最终发送前再次核验。
- 竞态测试：编辑期间需求变化、锁获取期间变化、最终点击前变化均不发送。
- 回归测试：首次发送、再次发送、发送结果未知恢复及只读日程边界。
- 全量 Node 与 Python 测试。
- 本机 8765 部署、健康检查和只读实机确认；未经用户单独授权不执行真实发送。
