# 项目管理卡片快速呈现设计

## 目标

进入项目管理时，不再等待全部项目详情请求完成后才统一显示卡片。管理员端和同事端都应先显示当前用户有权限查看的本地项目卡片，再在后台完成原有详情同步。

## 根因

当前页面先读取项目摘要，再为每个项目并发读取详情，并在所有详情请求结束后统一渲染。实测管理员账号可见 53 个项目，摘要请求约 71 毫秒，53 个详情请求整体约 825 毫秒，因此卡片出现存在明显延迟。同事端使用相同链路，只是按项目归属过滤后通常请求数量较少。

## 方案比较

1. **分阶段呈现并保留后台同步（采用）**：使用现有项目和考试列表接口组成卡片所需的本地数据，先渲染卡片；原有详情请求继续在后台执行，完成后更新卡片。首屏快且不改变同步行为。
2. **新增项目卡片专用后端接口**：由服务端一次返回完整卡片数据。接口更清晰，但需要同时修改前端、Node 服务和 Python 数据层，改动范围较大。
3. **仅缓存上次项目列表**：再次进入页面时可立即显示，但首次进入仍有延迟，而且缓存失效策略会增加状态复杂度。

## 设计

- `loadProjects` 先并发读取现有 `/api/tasks` 与 `/api/exams` 数据。
- 按 `taskId` 将场次数据合并到项目摘要中，生成项目卡片当前需要的项目名称、客户名称、来源账号、场次数量、状态和进度。
- 第一阶段数据到达后立即更新 `taskViewState.tasks` 并调用 `renderProjectList`。
- 随后保留现有项目详情请求；全部完成后再次更新状态并调用 `renderProjectList`。
- 列表接口和考试接口已有相同的项目归属权限过滤，管理员与同事仍只能看到原有权限范围内的数据。
- 刷新按钮继续执行相同的分阶段加载，不增加缓存，也不修改项目详情、考试列表或自动配置的数据流。

## 并发与错误处理

- 第一阶段请求失败时沿用当前错误展示，避免显示不完整或越权数据。
- 单个详情请求失败时继续沿用摘要数据，不影响其他卡片。
- 若连续触发刷新，较早请求不得覆盖较新的结果；实现时通过加载序号只提交最后一次加载结果。

## 验证

- 新增失败测试，证明第一阶段渲染发生在详情批次完成之前。
- 验证详情批次完成后仍会执行第二次渲染，保留现有同步行为。
- 验证项目和考试数据按 `taskId` 合并，且不改变项目筛选、搜索和卡片操作。
- 运行现有 UI、路由、服务配置和权限相关测试。
- 同步到本机 8765 运行环境后，分别验证管理员与同事权限过滤不变，并测量卡片首次出现时间。
