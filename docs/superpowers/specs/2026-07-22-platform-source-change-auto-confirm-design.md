# 平台内部来源变更自动确认设计

## 背景与根因

项目详情中的运控协同步骤会显示“有变更请确认”。当前提示不是来自一条真正的待审核记录，而是页面只要发现 `projectSourceChangeHistory` 中存在任意泛微或易考需求修改历史，就持续显示黄色提示。该历史是追加式审计记录，没有待确认状态、确认按钮或确认接口，因此用户无法找到确认入口，历史记录也会让提示永久存在。

目前 `projectSourceChangeHistory` 只由项目平台内的来源编辑接口生成：项目用户打开泛微业务需求或易考需求单，在平台内修改并保存后，服务端写入新版本和变更历史。这类操作已经是管理员或项目负责人作出的明确人工决定，不应再次要求同一个内部人员确认。

## 统一业务规则

1. 管理员和普通项目负责人在项目平台内直接修改并保存泛微业务需求或易考需求单，均属于“平台内部人工修订”。
2. 平台内部人工修订保存成功即自动确认；保留版本、字段前后值、修改时间等审计信息，但不产生“有变更请确认”提示。
3. 该规则统一适用于全部运控协同模块，包括建批次、人员任务、内容任务、运控归档，以及后续新增的协同模块。
4. 客户、微信群或其它外部来源提出的变更继续进入现有人工审核流程，必须采纳或驳回后才能进入执行；本次不改变外部变更审核规则。
5. 平台内部修订不新增确认按钮或确认接口，因为保存动作本身就是确认动作。

## 方案比较

### 方案 A：直接删除全部黄色提示

改动最少，但会失去未来对外部来源变更显示待审核状态的能力，也无法表达审计记录是否已自动确认，不采用。

### 方案 B：为来源历史增加统一审核状态（采用）

新增共享状态语义：平台内部修订写入 `reviewStatus: "auto_confirmed"`；未来若外部来源写入同类来源历史，则必须显式使用 `reviewStatus: "pending_review"`。所有运控协同模块通过同一个判定函数决定是否显示提示，不再各自推断“历史存在等于待确认”。

### 方案 C：增加人工确认按钮

能够清除提示，但让管理员或项目负责人重复确认自己刚保存的修改，与已确认的业务规则冲突，不采用。

## 数据设计

新生成的平台内部来源变更记录增加：

```json
{
  "source": "fanwei | examRequirement",
  "reviewStatus": "auto_confirmed",
  "changedAt": "ISO-8601",
  "versionBefore": 1,
  "versionAfter": 2,
  "changes": []
}
```

- `auto_confirmed`：平台内管理员或项目负责人保存的人工修订。
- `pending_review`：预留给未来进入同类来源历史的外部变更。
- 现有记录没有 `reviewStatus`。由于当前历史只由平台内来源编辑接口生成，兼容读取时将无状态旧记录视为 `auto_confirmed`，不执行数据库批量迁移。
- 对未知且非空的状态采用保守策略，视为需要审核，避免未来新增状态被静默放行。

现有客户/微信群变更继续使用需求中心的 `changeRequests`、`pending_internal_review`、采纳和驳回接口，不并入 `projectSourceChangeHistory`。

## 页面行为

### 运控协同卡片

- 建批次、人员任务、内容任务、运控归档统一调用共享的来源变更审核判定。
- 只有影响该模块且审核状态为待审核的外部来源记录，才显示“有变更请确认”。
- 平台内部修订以及兼容识别的旧记录不显示黄色提示，也不改变模块原有的可执行、待同步、等待批次或已完成状态。

### 需求变更记录

- 项目详情继续展示平台内部修订的字段前后值、版本和时间。
- 内部记录明确显示“平台内部修改 · 已自动确认”，让用户知道无需寻找额外确认入口。
- 外部待审核变更继续在现有需求变更区域显示采纳/驳回操作。

## 服务端行为

- `source-snapshot` 保存泛微或易考需求来源时，在新增历史记录中写入 `reviewStatus: "auto_confirmed"`。
- 不新增确认 API，不删除审计历史，不修改外部需求变更状态机。
- 现有记录兼容逻辑只作用于展示和门禁判定，不重写历史数据。

## 测试与验收

1. RED 测试证明：当前只要存在平台内部历史，建批次、人员任务、内容任务和运控归档都会错误显示“有变更请确认”。
2. 服务端测试验证泛微和易考需求的平台内保存均写入 `reviewStatus: "auto_confirmed"`。
3. UI 单元测试验证：
   - `auto_confirmed` 记录不触发任何运控协同模块的黄色提示；
   - 旧的无状态记录按内部修订处理，不触发提示；
   - `pending_review` 和未知非空状态仍按来源影响范围触发提示；
   - 内部审计记录仍显示字段差异，并标注“已自动确认”。
4. 运行相关 Node 测试、全量 Node 测试和全量 Python 测试。
5. 原子同步并重启 8765，确认项目中的建批次、人员任务、内容任务、运控归档不再因内部历史显示黄色提示；外部待审核变更入口保持不变。

## 非目标

- 不清除或删除任何历史审计记录。
- 不自动采纳客户、微信群或其它外部变更。
- 不改变运控协同步骤的业务状态、执行按钮或数据来源映射。
- 不为内部人工修订增加重复确认流程。
