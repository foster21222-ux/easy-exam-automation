# 建批次详情修改入口同步设计

日期：2026-07-30  
状态：方案已由用户确认

## 问题

易考需求单的考试日期从 2026-08-22 修改为 2026-08-23 后：

- 项目工作流使用实时计算结果，正确显示“建批次 · 可修改”。
- 建批次详情仍展示初次创建草稿中的 2026-08-22。
- 打开建批次详情不会主动刷新批次修改状态；持久化状态仍为 `success` 时，“修改批次信息”按钮保持隐藏。

人员任务详情在打开时会主动刷新状态，建批次详情缺少对应逻辑。问题属于前端状态入口不同步，不是易考需求被旧草稿覆盖；数据库中的最新易考需求仍为 2026-08-23。

## 方案

采用最小前端修复，不改变既有批次修改业务规则：

1. 打开建批次详情时，立即根据项目工作流的批次状态渲染修改入口。
2. 对已有批次主动调用批次修改状态接口，刷新当前项目、期望快照、已应用快照和差异。
3. 状态读取期间显示“正在检查最新需求与运控已应用值”，不再保留无反馈的空白区域。
4. 状态为 `update_available` 时展示“修改批次信息”按钮，并在详情内展示受管字段的“运控已应用值 → 最新需求值”。
5. 点击按钮后的既有流程保持不变：先读取运控当前值生成预览，再由用户统一二次确认；进入详情本身不得修改运控。

不增加手工日期编辑框，不用最新需求覆盖运控已应用值，也不自动触发运控浏览器预检。

## 数据口径

- 初次创建草稿：只用于说明初次创建参数，不再作为批次修改入口的状态依据。
- 项目工作流状态：用于进入详情时立即确定是否应显示修改入口。
- `GET /operation-batch/update-state`：用于刷新期望快照、已应用快照和精确差异。
- `POST /operation-batch/update-preview`：仅在用户点击“修改批次信息”后调用，用于读取运控当前值。

## 错误处理

- 修改状态读取失败时，保留外层工作流给出的“可修改”入口，并在详情显示明确错误；用户可以重新打开详情重试。
- 不得因为状态接口短暂失败把按钮静默隐藏。
- 项目已经切换时，丢弃旧项目的异步响应，避免跨项目污染。

## 验收

1. 外层为“可修改”时，打开建批次详情即可看到“修改批次信息”按钮。
2. 详情展示 2026-08-22 → 2026-08-23 的概况日期和日程时间差异。
3. 点击按钮后能生成同样的只读预检确认窗。
4. 未点击最终确认前，运控数据不发生变化。
5. 状态接口失败时显示可理解错误，并保留重试入口。
6. 相关前端回归测试、Node 全量测试和 Python 全量测试通过；8765 页面完成实际验证。
